# Plan: F3 to F7, the agent answers

You asked for the rest of the v1 features to be built in one run, so this one plan covers F3 to F7, on one branch with one commit per feature and one pull request. The branch starts from the F2 branch, so it also depends on pull request #2.

## Goal
After this, a parent's WhatsApp message gets a reply: a warm, short answer from the handbook in the parent's language (English, Shona or Ndebele), checked by code before it goes out, or a fixed holding message plus a hand-over row for the admissions office when it is an exception. Every decision is logged with its checks and cost.

## Feature
- F3: a Shona or Ndebele message is sorted by Claude into the same labels. AC1.
- F4: the rules R1 to R9 decide in code what the agent may do. AC1 to AC4.
- F5: Claude writes the reply from the handbook and the saved history, and code checks it, with one fix attempt. AC1, AC3, AC5.
- F6: an exception sends a fixed holding reply and writes a hand-over row with the reason. AC2, AC4.
- F7: the reply goes out through 360dialog, and every decision is logged with its cost. AC1, AC5.

## Steps
1. **F3, Claude sorts non-Jev messages** (`src/lib/reader.ts`). When Jev leaves the label empty (Shona, Ndebele, mixed or unsure language), Claude answers the same two questions with structured output checked by zod. The message is data in a labelled block, never part of the instructions. Failure or invalid output stores `engine = error` and the message goes to a person. Done when unit tests (fake Claude) pass and the migration adds `claude` to the allowed engines.
2. **F4, the rules in code** (`src/lib/rules/`, `src/lib/handbook.ts`): `decide()` returns answer or hand over, with a reason, from the label and the message; `checkReply()` runs the reply checks. One file per rule group, and every rule has at least one unit test whose name starts with its id, R1 to R9. Allowed dollar amounts are read from the handbook file, not typed into code. Done when `npm test` shows the R1 to R9 tests passing.
3. **F5, Claude writes the reply** (`src/lib/writer.ts`). It gets the handbook text, the last 10 messages as quoted context, and the parent's message, and returns `{ reply, language }` checked by zod. Code then runs `checkReply()`. A failed check gives Claude one retry that names what failed. A second failure is a hand-over. Done when unit tests (fake Claude) show a good reply passes, a bad one is fixed once, and a twice-bad one is handed over.
4. **F6, hand-overs** (`src/lib/handover.ts`, new table `academy_handovers`): a fixed holding reply in English, Shona or Ndebele (the wording is my draft and needs a native speaker's review) and a row with the reason (`not_in_handbook`, `bypass_attempt`, `complaint`, `health_safety`, `money`, `low_confidence`, `check_failed`, `model_error`, `unsupported_language`). Done when unit tests show each reason creates one row and one holding reply, and the database test saves and reads one back.
5. **F7, send and log** (`src/lib/send.ts`, `src/lib/agent.ts`, new table `academy_decisions`, outgoing rows in `academy_messages`): the agent runs after the webhook has answered 200 (using Next's `after`, so 360dialog is never kept waiting), for each new message. It sends through the 360dialog sandbox, saves the outgoing message, and writes one decision row: status, reason, checks and results, model, tokens, cost, latency. A cap of 20 replies per conversation per 24 hours stops a loop from running up cost. Done when unit tests (fake send, fake Claude, fake memory) cover the full path, and the database tests cover the new tables.
6. **End-to-end cases** (`npm run cases:agent`): T01 to T05 run through the real pipeline with the real Jev and Claude, a fake sender, and a fake database, and check the acceptance criteria wording (450, 680, no "confirmed" or "booked", no "guarantee", hand-over reasons). Done when it passes on 3 repeats. This needs `ANTHROPIC_API_KEY`.
7. **Live check** from the sandbox phone for AC1 to AC5, after the key is in Vercel.

## AI parts
- **Claude as reader (F3):** answers intent and language for messages Jev cannot read. Model variable `MODEL_READER`, default `claude-sonnet-5-5`. Output schema: the 15 allowed labels, the 5 languages, a confidence from 0 to 1. Invalid output is logged and routed to a person.
- **Claude as writer (F5):** writes the wording only. Model variable `MODEL_WRITER`, default `claude-sonnet-5-5`. Output schema: `{ reply: string, language }`. Code, not Claude, decides whether the agent may answer at all, which facts are allowed, and whether the reply may go out.
- **Code decides:** the routing (R4 to R7, R9), the amounts (R1), the place and visit wording (R2, R3), bank details (R8), the reply's language (R9), the hand-over, the send, the cap.
- **Expected cost:** about 1,500 input tokens (the handbook is short) and 150 output tokens per reply, about $0.005 per answered message at $2 per million input and $10 per million output tokens. Hand-overs cost nothing beyond Jev.

## Approval and data
- **What leaves the solution:** a WhatsApp reply to the sender, through the 360dialog sandbox only. Allowed on its own only when `decide()` says answer, the schema passes, and every reply check (R1, R2, R3, R8, R9) passes. A fixed holding reply goes with every hand-over. Everything else is held for a person.
- **Record before sending:** the decision row (status, checks, reason) is written before the send, and the outgoing message is saved after it. A failed send is logged and marked on the decision row.
- **Secrets, server side only:** `ANTHROPIC_API_KEY`, `D360_API_KEY`, `SUPABASE_SECRET_KEY`, `D360_WEBHOOK_SECRET`, `TYPESAFE_API_KEY`. You add `ANTHROPIC_API_KEY` to `.env.local` and Vercel yourself.
- **Personal data:** replies and message text are stored in locked Supabase tables only. Logs hold ids, labels, checks, status, tokens and cost, never message text or numbers. Test cases use made-up messages only. The sandbox phone's number is used only as the reply address.
- **Prompt injection:** the parent's words go to Claude inside a labelled data block after the instructions, never as instructions, and a bypass attempt is routed to a person by code before Claude writes anything.

## What could break
The riskiest part is step 5: the webhook now starts a model call and a send. Using `after` keeps 360dialog from waiting, but a crash after the 200 means no retry. The decision row, written first, shows what happened. Also, a wrong reply would reach a parent, which is why every reply check runs in code and a failure becomes a hand-over.

## Not doing
- Any page for the admissions officer (F9), templates mode (F8), images, voice notes, payments, and any real parent data.
- Putting a conversation in a "with a person" state that silences the agent.
- Replying in any language other than English, Shona or Ndebele.
